# MeetHub

Telegram-бот для командных дейликов: публикует напоминания о встречах, собирает отчёты в комментариях и выбирает ведущего.

## Возможности

- Несколько каналов со связанными группами обсуждений; управление из личного чата владельца.
- Расписание по дням недели (UTC+3), до одного дейлика в день. Время встречи и упреждение поста настраиваются кнопками.
- Пост со ссылкой на встречу, временем начала и, по желанию, случайным ведущим из авторов отчётов.
- Сводка планов из предыдущего треда и игнор-лист авторов для каждого канала.
- Доска MR: закреплённое rich-сообщение с таблицами и ссылками на MR в группе обсуждений по данным GitLab; три вида группировки на канал (необязательно).
- Настройки и отчёты в PostgreSQL, уведомления владельцу о сбоях.

## Быстрый старт

Нужны Docker Compose и Telegram-бот, созданный через [@BotFather](https://t.me/BotFather). Узнайте свой Telegram ID для `TELEGRAM_OWNER_ID`.

```sh
git clone https://github.com/passwordhash/meethub-bot.git
cd meethub-bot
cp .env.example .env
```

Заполните `.env`, затем запустите приложение:

```sh
docker compose up -d --build
```

Compose поднимет PostgreSQL, применит миграции и запустит бота. Логи: `docker compose logs -f bot`.

Для локального запуска без Docker: установите Go 1.23+ и PostgreSQL, задайте переменные из `.env` в shell, затем выполните `make migrate` и `make run`.

## Настройка бота

1. Напишите боту `/start` от имени владельца.
2. В личном чате отправьте `/connect <ID канала>`. Вы должны быть администратором канала; боту нужны права администратора и публикации. Бот также должен иметь право отправлять сообщения в связанной группе.
3. Снова отправьте `/start`, выберите канал и настройте его на одном экране:
   - кнопка дня недели: бот попросит время дейлика в формате `ЧЧ:ММ` (UTC+3, любая минута); там же можно убрать день или отменить ввод;
   - «Пост за N мин»: упреждение 15, 30, 60, 120 минут или своё целое число от 0 до 1439; пост может выйти накануне дейлика;
   - «Ведущий»: включает или выключает выбор ведущего из отчётов.
   - «Игнор-лист»: Telegram ID пользователей, чьи сообщения бот не считает отчётами: они не попадают в сводку и выбор ведущего. ID добавляется кнопкой «Добавить», удаляется нажатием на него. Отчёт, сохранённый до добавления в список, остаётся в текущей сводке.
   - Участники MR определяются автоматически: укажите Telegram username в поле Twitter профиля GitLab, например `@yarik`. Ручное меню отключено, прежние настройки сохранены, но не используются.
   - «Вид доски» (только если настроен GitLab): кнопка-цикл «по мячам» → «по ревьюверу» → «по проекту»; доска перерисуется при следующем опросе GitLab.

Поддерживаются `/start` и `/connect`. Любая команда отменяет ожидание ввода.

Чтобы бот видел отчёты, отключите Privacy mode через BotFather и заново добавьте бота в группу обсуждений.

## Доска MR

Если заданы `GITLAB_URL`, `GITLAB_TOKEN` и `GITLAB_GROUP`, бот раз в `GITLAB_POLL_INTERVAL` (по умолчанию 90 секунд, не чаще 30 секунд) читает открытые MR группы и статусы ревьюверов и ведёт в группе обсуждений каждого подключённого канала при наличии участников одно закреплённое rich-сообщение (Bot API 10.1) — доску MR. Термины — в `CONTEXT.md`, решения — в `docs/adr/0001-gitlab-polling-for-mr-board.md` и `docs/adr/0002-rich-messages-for-mr-board.md`.

- Доска — таблицы Markdown со ссылкой на каждый MR (`web_url`); титул обрезается до 48 символов, `|` в титулах экранируется. В GitLab бот ничего не пишет. Трункации нет: лимит rich-сообщения 32 768 символов покрывает всю команду.

- Токену достаточно scope `read_api`; бот обращается к `GET /users/:id` для профилей, `GET /groups/:id/merge_requests` и `GET /projects/:id/merge_requests/:iid/reviewers`, читая все страницы обоих списков (максимум 50 страниц каждого списка). `GITLAB_URL` должен указывать непосредственно на GitLab: HTTP-редиректы не выполняются, чтобы не передать токен другому серверу.
- На доску попадает открытый MR не в Draft, с ревьюверами, у которого автор или хотя бы один ревьювер — участник команды. Участники определяются по полю Twitter профиля GitLab: Telegram username из 5–32 латинских букв, цифр и `_`, начинается с буквы, с необязательным `@`. Состав общий для всех каналов. Профиль запрашивается один раз на пользователя за цикл опроса; пустое или некорректное значение не включает пользователя в команду. Ошибка получения профиля отменяет обновление доски до следующего опроса. Смерженные и закрытые MR исчезают при следующем опросе.
- Разделы: «Ждёт ревью», «Ждёт правок автора», «Апрув, ждёт merge». Значки ревьюверов: 💬 — прокомментировал, ✍️ — запросил правки, ✅ — апрувнул, 🔁 — повторное ревью. Время в строке — сколько MR находится в текущем разделе.
- Вид доски настраивается на канал кнопкой «Вид доски»: «по мячам» (дефолт; три раздела-таблицы, строки по возрасту ожидания), «по ревьюверу» (блоки «X смотрит» по ждущим ревьюверам и «Y должен» по авторам, апрувы одной таблицей) или «по проекту» (таблица на проект по алфавиту, мяч — бейджем ⚡ в строке).
- Историю статусов GitLab не хранит, поэтому бот запоминает её сам: 🔁 и время появляются только для переходов после запуска; для MR, впервые увиденного ботом, отсчёт идёт от его последнего обновления в GitLab.
- Боту нужно право закреплять сообщения в группе. Без него доска не публикуется, и владелец получает уведомление. Если доску открепили, бот закрепит прежнее сообщение; если удалили — создаст новое. Ошибки прав, rate limit и временные сбои не приводят к пересозданию: бот повторяет попытку на следующем опросе. При переходе со старой plain-версии бот снимает прежний пин и пинит rich-доску заново; старое сообщение остаётся в чате откреплённым.
- Если среди авторов и ревьюверов открытых MR больше нет участников, существующая доска обновляется до «Открытых MR команды нет.». В каналах, где доски ещё не было, без участников она не создаётся.
- Bot API возвращает только последнее закреплённое сообщение. Если закрепить другое сообщение, бот снова закрепит доску; старые сообщения при восстановлении не удаляются.

Без этих переменных доска выключена, а пункт «Вид доски» не показывается. Ручная конфигурация участников отключена независимо от наличия GitLab.

## Публикация и данные

Пост содержит дату и время дейлика (UTC+3), `MEETING_URL` и выбранного ведущего. Он выходит за заданное число минут до встречи, в том числе накануне. Бот проверяет расписание каждые 15 секунд и может догнать задержавшийся пост до начала дейлика. После начала пропускает его и уведомляет владельца. На дату дейлика выходит один пост; изменение времени после публикации подействует со следующей недели.

### Отчёты и ведущий

- Пишите отчёт прямым ответом на автопересланный пост последнего дейлика в группе обсуждений. Учитываются текст и подписи к медиа; сообщения ботов и ответы на чужие комментарии не учитываются.
- От каждого участника сохраняется первый отчёт. Его правки учитываются до подготовки следующего поста; последующие сообщения не заменяют отчёт.
- При следующей публикации бот берёт отчёты предыдущего дейлика и отправляет сводку в новый тред. Извлекает раздел «Сегодня», «На сегодня», «Сделаю сегодня» или «Задачи на сегодня»; если непустого раздела нет, берёт весь текст. Длинную сводку разбивает на сообщения.
- Ведущий выбирается случайно из авторов этих отчётов. Предыдущий ведущий не участвует в выборе, если есть другие кандидаты. Без отчётов строка с ведущим не добавляется.

### Хранение и ограничения

Тексты отчётов и их снимков очищаются через 30 дней при ежедневной очистке. Резервные копии автоматически не создаются. Миграции не содержат `Down`, чтобы откат не удалил пользовательские данные. Отключение привязки канала пока не реализовано.

При обновлении прежние cron-расписания вида `М Ч * * ДНИ` переносятся в сетку с сохранением времени постов. Остальные сбрасываются с уведомлением владельца.

## Разработка и деплой

```sh
go test ./...
make lint
```

Для деплоя укажите SSH-адрес сервера и путь к клону репозитория на нём:

```sh
DEPLOY_SERVER=user@server DEPLOY_PATH=/path/to/repository ./deploy.sh
```

На сервере должны быть настроены SSH-доступ и `.env`. Скрипт обновит рабочую копию и выполнит `docker compose up -d --build`. Резервные копии не создаются.

## Конфигурация

Скопируйте `.env.example` в `.env` и задайте значения. `MEETING_URL` должен быть HTTPS-ссылкой; `POSTGRES_HOST` для локального запуска — `localhost`, Compose сам использует адрес `db`.

Не коммитьте `.env` и не передавайте реальные секреты в issue или логи.
