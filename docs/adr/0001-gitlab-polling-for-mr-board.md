# 0001. Доска MR получает данные опросом GitLab API, а не webhook'ами

Дата: 2026-10-28. Статус: принято.

## Контекст

Запросы на ревью теряются в треде под недельным постом: непонятно, какие MR открыты, у кого мяч и какие требуют повторного ревью. Решили вести доску MR — закреплённое сообщение, которое строится только по состоянию GitLab. Telegram-сообщения с `#ревью` бот не разбирает.

Бот получает обновления Telegram через long polling (`getUpdates`). HTTP-сервера у него нет, порты в `docker-compose.yml` наружу не открыты.

## Решение

Бот раз в 1–2 минуты опрашивает GitLab API токеном со scope `read_api` и перестраивает доску. Источник правды — GitLab: состав MR, ревьюверы, reviewer state, merge/close. Ручных статусов в Telegram нет.

## Последствия

- Не нужны публичный адрес, HTTP-сервер и настройка хуков на проекты.
- Доска отстаёт от GitLab до интервала опроса. Для трекинга ревью это приемлемо.
- Без пингов: доску бот только редактирует, персональные уведомления по-прежнему шлёт GitLab.
- Reviewer state есть в API (проверено 2026-10-28 на gitlab.pinkzone.dev): `GET /projects/:id/merge_requests/:iid/reviewers` отдаёт `unreviewed`, `reviewed`, `requested_changes`, `approved`.
- Токен fine-grained: инстансные `/merge_requests?reviewer_username=…` и `/version` закрыты, `GET /groups/:id/merge_requests` открыт. Поэтому опрос — открытые MR группы плюс `/reviewers` на каждый MR с ревьюверами (≈30 запросов за цикл на 2026-10-28).
- GitLab не хранит историю статусов ревьювера. Повторное ревью и время в текущем состоянии бот выводит сам, запоминая прошлый статус каждой пары «MR × ревьювер» и время его смены.
- Webhook'и можно добавить позже, если задержка станет проблемой. Модель доски от этого не меняется.
